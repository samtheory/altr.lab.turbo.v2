# Shared engine — sharpening decisions

> Decision record. **Current brief for agents: [[README]].** This note and that brief match. Intent: [[../../feature_list/Jord/00-intent]]. Layout: [[../../feature_list/Jord/02-architecture]].

Chosen on 2026-10-18; refined the same day (pragmas, `records` shape, snapshot). Code does not start from this note. **Slice 0 scope only** — one file, one library, one Hono process. No Postgres, Redis, Mongo, or extra servers.

## What we are building first

A single libSQL **file** inside this repo (`data/jord.db`). `@altr/jord` opens it. One Hono server under `cloud/jord` is the only new process. Artemis’s future bot and the API share that file. Other database engines stay a seam in the design and are not installed.

PocketBase stays in `cloud/pocketbase` and is not this database.

## Why a file

libSQL speaks SQLite and runs as a file (`file:./data/jord.db`). You carry the lab by copying that file. No Turso account, no Docker, no Postgres server. The same `@libsql/client` can point at hosted Turso later by changing the URL. `sqlite-vec` can be added on this file when the Artemis bot needs search — not in Slice 0. That is why this file is the right first store for the bot, and why a hosted-only database is the wrong start. Full layout: [[../../feature_list/Jord/02-architecture]].

The file is gitignored. The repo records the path and the schema. You carry the data file yourself so bot notes never land in git.

### Disaster recovery

`data/jord.db` is untracked. Before high-write services (Artemis ticks, long API sessions) run against a machine you care about, a **minimal snapshot** is required: root script `pnpm db:snapshot` (or equivalent) using SQLite’s online backup API against that file. Helper lives with the Jord client (`@altr/jord`); it must not invent a second database. Local state must survive cleanouts and disk mishaps without relying on git.

## Storage engine config

Every connection that opens `data/jord.db` in Slice 0 **must** apply these connection-level pragmas (libSQL / SQLite):

| Pragma | Value |
|--------|--------|
| `journal_mode` | `WAL` |
| `busy_timeout` | `5000` |
| `synchronous` | `NORMAL` |

**Rationale:** WAL plus a busy timeout lets Artemis (bot logging / ticks) and `@altr/jord-server` read while the other writes, instead of failing with `database is locked`. `synchronous = NORMAL` is the usual WAL companion for durability versus throughput on a local file. No second process, no Redis — concurrency is the file’s WAL mode.

## Dialect seam

Drizzle owns the schema from Slice 0, with the libSQL driver only. `DATABASE_URL` must be a `file:` URL. Any other scheme fails with a clear error until a later slice allows it. One schema module, one URL, drivers added when a plan says so.

## First table

### Role of `records`

`records` is a **generic JSON document / key-value / agent scratchpad** store. Buckets separate apps (`lab`, later `artemis` for agent notes). It is **not** the Artemis trading ledger.

**Boundary:** typed trading entities — `orders`, `positions`, `trades`, and peers — must **not** live inside `records.body`. Those get strictly typed Drizzle relation tables in later slices when the trading schema lands. Slice 0 does not create those tables.

### Schema (agent / vector-ready, no sqlite-vec yet)

| Column | Type | Notes |
|--------|------|--------|
| `id` | text, primary key | cuid2 or uuid on insert |
| `bucket` | text, not null | App / agent namespace |
| `body` | text, not null | JSON document |
| `metadata` | text, optional | JSON for arbitrary tags; null allowed |
| `created_at` | integer, not null | Unix milliseconds |
| `updated_at` | integer, not null | Unix milliseconds; set on insert and update |

**Index (required):** composite on `(bucket, created_at)` so multi-bucket reads do not full-scan the table.

No embedding column in Slice 0. Vector search is a later attachment on this same file.

## Name

**Locked: Jord.** Later admin app: **Jord Studio**. Library package: `@altr/jord`. Shared utils stay in `@altr/base`. Docs folders: `idea/Jord`, `feature_list/Jord`, `plan/Jord`. The data file is `data/jord.db`.

The brief is the same as **Lode**: a short name for a store in the ground. Greek and Norse names were checked on 2026-10-18. Collisions are listed under reject.

**Reject**

| Name | Why |
|------|-----|
| PolyBase | Microsoft SQL Server feature |
| AltrBase | Reads as the package `@altr/base` |
| Keel | Keel.sh is a backend product |
| Urd / Urðr | Already used for database reflection and for AI-agent memory |
| Mimir, Munin, Huginn | Grafana Mimir, Munin monitoring, Huginn agent |
| Leto | Mother of Artemis, but Letos is a SQLite desktop app |
| Fulla | `fulla.dev` is an identity server |
| Atlas, Iris, Hestia | MongoDB Atlas, InterSystems IRIS, HestiaCP |

**Chosen: Jord.** Shortlist below is the record of what was compared.

| Rank | Name | Source | Why it fits |
|------|------|--------|-------------|
| 1 | **Jord** | Norse earth, mother of Thor | One syllable, same weight as Lode. The file is the ground the other products stand on. |
| 2 | **Idunn** | Norse keeper of the apple chest | She stores the thing the gods live on. Fits a file you carry, and later bot memory in that chest. `idunn.no` is a publisher, not a database. |
| 3 | **Omphalos** | Greek navel-stone at Delphi | The stone in the ground that marks the center. Closest myth to a lode. Three syllables. |
| 4 | **Plouton** | Greek god of wealth under the earth | The mine itself. Two syllables. Quieter than the Roman name Pluto. |
| — | **Lode** | English | Still the clearest non-myth word. Kept as the benchmark the myth names have to beat. |

Plinth and Cairn stay available and are not myth names. Clotho (the Fate who spins the thread) is a spare; an old lab project already used it for data schemas.
